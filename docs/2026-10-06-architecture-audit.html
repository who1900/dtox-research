Архитектурный аудит dtox-research

Основной долг находится в управлении состояниями и ownership индексов, а не в выборе Qdrant или BM25. Направление решения: модульный монолит, один владелец синхронизации и никаких новых сервисов.

Без изменений кода, deploy, платежей, секретов, commits и длинных тестовых прогонов

Рамки доказательств

Production-наблюдения помечены явно. Hash pipeline/service.py совпал с production; hash pipeline/extractor.py также совпал. Только нормализованный LF hash api/main.py отличается: local 070e1e..., production c7fc69..., поэтому локальные API-находки не являются production-фактами. Все source links относительны.

Performance- и quality-числа не оценивались. В отчёте использованы только переданные live-наблюдения и локальные чтения кода.

Выводы

P1 / production подтверждено

Parser exception может стать успешным коротким извлечением

В production catch широкого parser exception в pipeline/service.py:2818-2829 создаёт fallback из первых 1700 символов. Он записывается в chunk cache, затем выставляются status=chunked и extractor_version=4; downstream получает короткий fallback как chunked.

Свести: явный parser result со status, quality и provenance. Ошибка не должна подменять прежний хороший индекс коротким fallback-текстом. pipeline/service.py; pipeline/extractor.py.

P1 / production подтверждено

Reprocess удаляет старое до проверки нового

Reset helper поддерживает удаление FTS, но включённый и активный timer запускает --feed --apply --skip-fts: пустые fts_ids пропускают FTS delete, поэтому FTS rows остаются. Этот запуск удаляет Qdrant points и caches до успешного refetch; при неудаче прежние points и caches утрачены, а оставшиеся lexical rows могут быть устаревшими. Timer и service настроены на one-shot; неактивность между 15-минутными запусками ожидаема.

Свести: сначала загрузить и проверить replacement, затем публиковать revision; прежнюю revision держать до подтверждения commit нужных представлений.

P1 / поведение следует из кода; live wrong-order не подтверждён

Repair вставляет пропущенный текст в конец section

Planner: строка 515-517 назначает новым chunks индексы после максимального существующего. Exact-section reader сортирует по chunk_index и собирает текст по этой последовательности. UUID идентифицирует chunk, но не кодирует исходную позицию.

Если gap находится внутри старого chunk, уже содержащего текст до и после пропуска, одного столбца source_position недостаточно для восстановления внутреннего порядка. Read contract должен собирать canonical normalized section assembly from source отдельно от stable point UUID. Single writer может materialize section text и chunks; UUID нельзя менять вслепую. Unit test проверяет missing text, live неправильный порядок не наблюдался.

P2

Repair имеет отдельного writer-а и ledger

Три файла planner, apply и runner составляют 2129 строк по проверенному снимку и вводят отдельные state/journal переходы. Штатная очередь в pipeline/service.py:3054-3181 ведёт coarse index, paper FTS, chunk FTS и metadata, но не является full-text vector writer-ом. Поэтому просто вызывать её из repair нельзя.

Свести: один owner для index sync. Repair выдаёт валидированный change job этому owner-у; durable journal и crash resume сохранить.

P2 / live journals не являются повреждением

FTS collision probe не доказывает глобальный UUID identity

apply_missing_prose_repair.py:544-567 использует AND из четырёх или более уникальных английских слов длиной от пяти символов. Так как point_id в FTS unindexed, lexical probe не доказывает глобальное существование или отсутствие UUID. Текст с недостаточным количеством токенов блокируется. Три production записи manual_attention имели journal prepared; свидетельств partial mutation или corruption нет.

Свести: точная проверка через indexed key/receipt или side catalog point_id -> row_id.

P2 / риск, не доказанный live hang

Глобальный data_version конфликтует с любым FTS write

Preflight, строки 704-707, отклоняет snapshot при изменении SQLite data_version. Несвязанная обычная FTS запись может вызвать конфликт и риск starvation. Live hang не доказан.

Свести: проверять revision только ремонтируемого paper; unrelated FTS writes не должны конфликтовать.

P2

Retryability определяется текстом exception

Runner, строки 678-687, ищет английские слова/фразы в сообщении, чтобы отличить transient ошибку. Текстовая правка может сменить retry на blocked или наоборот. Свести: typed code и явное поле retryable.

P2 / не скрытый переход в done

Frontier drained не различает непроверенное и полную проверку

frontier_drained и exit 0 сами не меняют papers.status и не означают healthy. Проблема итогового coverage: missing source, cache и unsupported могут быть исключены из unresolved_count, так что итог не отличает safe out-of-scope от uninspected.

Свести: отдельно показывать inspected, resolved, safe out-of-scope и unresolved. Не трактовать отсутствие inputs как полную проверку.

P2

Build cursor и top-up имеют разные гарантии

Обычный build, строки 138-150, записывает страницы и cursor; конечный cursor None начинает следующий проход сначала, без явного уникального ограничения на повторные строки. --topup дедуплицирует snapshot существующих point_id и добавляет новые ID в набор по мере прохода, но игнорирует canonical side catalog. Это не доказывает, что каждый top-up создаёт duplicates.

Свести: хранить явный completed state отдельно от cursor и дедуплицировать по общей canonical identity.

P2 / source identity

Mastercoin slug указывает на Tendermint

pipeline/whitepapers.py:45 сохраняет старое соответствие; runtime catalog содержит override. Нужна canonical migration с legacy alias и provenance, а не ещё одно исключение.

Вторичные локальные наблюдения

Не production-верификация: локальный normalized hash api/main.py отличается от production.

X402 contract дублируется: tools.ts:120 задаёт schema get_code с четырьмя полями и constraints, а payments.ts:59 вручную задаёт JSON Schema только с paper_id и target_elements. upstream.ts:63 повторяет English regex classification. Свести к общей Zod source schema и generated JSON Schema; сохранить запрет signed upstream retry в upstream.ts:81. X402_EVM_NETWORK alias не считать дефектом.

  • Search mode matrix разветвляет hierarchical retrieval, chunk lexical и paper lexical; отдельный paper-level ranker в _rank_papers. Конвергенция: одна production search policy и общие channel status/fusion; выключенные эксперименты удалять только после evidence.
  • RRF tie-break в ветке без rank channels сортирует множество только по score. При равенстве возможен нестабильный порядок. Только локальная гипотеза.
  • Hierarchical fallback возвращает legacy результаты; marker добавляется только для coarse_fallback. Прочие fallback причины могут не попасть в diagnostics. Только локальная гипотеза.

Live ledger snapshot

447 records = 6 applied_partial + 277 blocked + 3 manual_attention + 14 no_change + 1 retry + 146 outside. Отдельно зафиксировано 41 new chunks: chunks и records являются разными единицами учёта.

Это не число повреждённых papers, не независимая проверка vectors и не подтверждение полного corpus coverage. Три manual_attention имели prepared journals, без свидетельства partial corruption.

Сохранить и исправлять

Сохранять WAL, atomic cache writes, deadlines, resource caps, dry-run, old-vector checks, source provenance и authentication. Это полезные защиты.

  1. Parser result status/quality и nondestructive reprocess.
  2. Canonical normalized section assembly from source отдельно от stable UUID; учитывать gap внутри старого chunk.
  3. Один index-write contract для normal pipeline и repair, durable journal и typed errors.
  4. Одна production search policy, shared channel status/fusion; retire experiments только после evidence.

Минимальные acceptance invariants

  • Parser exception не считается завершённым качественным результатом.
  • При failed reparse прежний paper остаётся доступен.
  • Middle-gap prose читается в правильном порядке без изменения UUID старых chunks.
  • Unrelated FTS write не ломает preflight; revision conflict того же paper блокируется.
  • Crash/resume идемпотентен и доводит все индексы до согласованного состояния.
  • Missing inputs не выглядят как healthy completion; safe out-of-scope отличим от uninspected.
